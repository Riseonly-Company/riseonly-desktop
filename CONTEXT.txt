================================================================================
riseonly-desktop — READ THIS BEFORE YOU TOUCH ANYTHING
================================================================================

WHAT THIS IS

A native desktop client for Riseonly, written in Rust on the GPUI toolkit,
targeting macOS, Linux and Windows from one codebase. It is a 1:1 architectural
port of riseonly-ios: same layers, same module boundaries, same store triad,
same data engine, same performance contract. Screens and stores mirror the iOS
reference; only the application shell differs, because a phone has no window.

Right now only macOS is built and run. Linux and Windows code paths are written
but unexercised. That is deliberate: writing them blind now is cheap, retrofitting
them later is not. Never collapse a platform seam just because only one arm is
currently tested.

STATUS: Phases 0-3 done, Phase 4 nearly closed, Phases 5 and 6 gated, Phase 7
begun. 1,955 tests green on macOS.

The engine (wire, encrypted store, sync, outbox) is built headless with contract
tests, the fifteen platform seams are in, and the media bet has landed: the
zero-copy texture path, the video decoder and feed scheduler, the whole audio
stack (cpal + symphonia, gapless, resampling) and the whole sticker stack
(vendored rlottie, one shared tick, texture atlas), each with a memory-ceiling
test. What Phase 4 has left needs a render target.

The design system exists. Material tokens and their painted tier; typography
over a font the product ships itself rather than the host's; spacing, icon and
shell-geometry tokens; the SF-Symbol-to-Lucide table, keyed by the Apple name so
a ported screen still diffs against its Swift; flags as assets instead of
regional-indicator arithmetic; 41 locales with both interpolation dialects and
the fallback chain; a text input built on gpui's own IME plumbing; the RiseGlass
Swift bridge with real NSGlassEffectView regions; the left rail; and a storybook
that stands every stateless component at two appearances and three densities.

The shell responds. Adaptive columns are wired to the real window and are
reversible — narrowing merges columns rather than stacks, so widening restores
what was there. The active screen is a SET of visible-resource leases, and the
once-per-cycle rule is per key and global, which is what stops a window drag
from re-fetching. SessionActivity keeps the socket while unfocused, the
inversion of the phone. The keyboard reaches everything: Cmd/Ctrl+1..9, the
command palette, back and forward, Esc down the overlay stack. Right-click menus
and drag-in are placed and policed entirely inside the window rectangle, because
gpui has no popups off Wayland. A second launch hands its links to the first.

The network is real. One socket over tokio-tungstenite with backoff, a
`Bearer.<jwt>` handshake and an application-level heartbeat, because the
gateway's silence reaper does not count protocol Pongs. The engine gained a
second, narrow transport for the two auth calls an unauthenticated client has to
make, which the socket's action gate refuses by construction.

Six modules exist: auth (accounts, credentials, the token lifecycle),
onboarding, session (the active-sessions list), presence, post (the feed) and
user (the profile). A signed-out launch shows onboarding and the step flow; a
signed-in one restores from the credential store, refreshes if the access token
has aged out, and opens the shell. The feed and a profile are real screens over
real data, with optimistic likes and an optimistic follow that reconcile and roll
back. The other sixteen modules are the rest of Phase 7.

docs/PLATFORM_MATRIX.md says, per seam, what is verified, what merely compiles on
the CI matrix, and what is only written. Read it before claiming any coverage.
Nothing in this repository has been run on Linux or Windows.

    cargo make dev-macos -- -riseStorybook     the design system, all six ways

THE RULE ABOUT CONTEXT.txt
--------------------------------------------------------------------------------

Every significant directory carries a CONTEXT.txt. Before you work inside a
directory, read its CONTEXT.txt and every CONTEXT.txt above it on the path.
They tell you what the directory owns, what it must never do, and which canon
applies. This repo is expected to grow past a million lines; these files are how
an agent that has never seen it avoids inventing a parallel architecture.

If you add a directory that owns a concept, add its CONTEXT.txt in the same
change.

--------------------------------------------------------------------------------
LAYOUT
--------------------------------------------------------------------------------

crates/    THE LIBRARIES — layered, reusable, each with its own CONTEXT.txt
  rise-core         identifiers, generations, StaleGuard. No UI, no OS, no engine.
  rise-i18n         41 locales, plurals, both interpolation dialects.
  rise-validate     every rule about what a user may type. Zero dependencies.
                    ALL validation goes through a schema here — see below.
  rise-engine       wire, store, sync, upload. The data layer.
  rise-platform     every OS difference behind traits, plus the gpui shim.
  rise-theme        design tokens: palette, radii, heights, density, materials,
                    typography, spacing, icons, shell geometry.
  rise-ui           primitives: BoxUi, MainText, ButtonUi, IconUi, FlagUi,
                    InputUi, skeleton, fonts.
  rise-widgets      composed: glass panel, in-window overlays, context menu;
                    sheets, notifier and the media viewer still to come.
  rise-media        video, audio, lottie, images, calls.
  rise-navigation   routes, pane policy, navigation store.

app/       THE APPLICATION — a binary, not a library
  src/main.rs       installs the theme, opens a window, hands over to app/
  src/app/          shell: root view, router, deep links, the rail, the
                    keyboard, the command palette, windows, the storybook
  src/core/         session activity, active screens, config, the engine bridge
                    (the socket host, its backoff and credential policy, and the
                    HTTP sender the engine's second transport is given)
  src/modules/      the 22 feature modules, as plain module trees

  Modules are an organisation of screens and stores, not independent products.
  They live inside the application and may reference each other directly, the
  same way they do in the iOS reference. The genuinely reusable, layered pieces
  are the crates above.

  There is no compatibility layer and no sai. Every store talks to rise-engine
  through its module's engine/, exactly as chat-actions.swift and
  message-actions.swift do in the reference.

  The engine carries two transports, and the second one is not a loophole. The
  socket carries everything; HTTP carries `auth.refresh_token` and tag
  availability, and ONLY those, because the gateway's socket action gate refuses
  an unauthenticated caller anything else — which is exactly what refreshing an
  expired token is. Same descriptor catalogue, same replay policy discipline. A
  method the socket can carry never appears there.

--------------------------------------------------------------------------------
THE THREE BOUNDARIES (CI fails on violation — scripts/check-boundaries.py)
--------------------------------------------------------------------------------

1. rise-engine never imports gpui or an OS crate.
2. #[cfg(target_os)] appears only in rise-platform and rise-media.
3. stores/ never imports rise_engine directly; engine/ never imports gpui.

These are not style preferences. (1) is what keeps the engine reusable on iOS,
Android and wasm later. (2) is what keeps three OSes from becoming three
codebases. (3) is STORE_ARCHITECTURE.md expressed as a check.

--------------------------------------------------------------------------------
VALIDATION GOES THROUGH rise-validate. ALWAYS.
--------------------------------------------------------------------------------

A bare `if value.len() < 3` in a store, a screen or a repository is a bug even
when it is correct today: it is a second copy of a server bound that will move.
Declare a `TextSchema` beside the field and let every layer read THAT.

  const TAG: TextSchema = TextSchema::new("tag").trim().lowercase().checks(&[
      Check::min_bytes(3).message("tag_too_short"),
      Check::charset(Charset::TAG).message("tag_invalid_characters"),
  ]);

`check` returns the NORMALISED value, so what was judged and what is sent cannot
differ. Violations are data carrying an i18n key, never a rendered sentence.
Schemas are `const`, so they cost nothing and live next to the field.

This is not defence in depth. `api/docs/VALIDATES_SUMMARY.md` records 712 fields
with no validation on ANY server layer — for much of the product this crate is
the only check there is. crates/rise-validate/CONTEXT.txt has the rest.

--------------------------------------------------------------------------------
ANYTHING THAT FLOATS OVER THE PAGE IS A ModalUi
--------------------------------------------------------------------------------

`rise_widgets::ModalUi` — a dialog, a confirmation, a picker, a hand-off, an
error the user has to acknowledge. If it dims the page behind it, it is that
component. A hand-rolled `div().absolute().inset_0().bg(scrim)` is a bug even
when it looks right.

  ModalUi::new("auth.telegram")
      .title(tr("tg_redirect_title"))
      .width(ModalWidth::Medium)
      .track_focus(&self.focus_handle)
      .on_dismiss(handler)
      .action(ModalAction::primary("open", tr("tg_redirect_open_btn")).on_click(..))
      .render(&theme, window, cx)

Four things it gets right that three hand-rolled ones each got a different
subset of: it is OPAQUE (a native material is below the Metal layer, so a
GlassPanel over page content shows the page through it), it OCCLUDES (or a
click on a button inside also hits the scrim and dismisses first), it FITS the
viewport (or there is no outside left to click), and Esc works.
crates/rise-widgets/src/modal_ui/CONTEXT.txt has the rest, including when to
reach for `ModalDismiss::Explicit`.

--------------------------------------------------------------------------------
DEBOUNCE COMES FROM rise-engine
--------------------------------------------------------------------------------

`rise_engine::Debouncer` — trailing, with a `with_max_wait` ceiling so a user
typing steadily still gets an answer, and cancellation by drop. One line in an
actor: `self.debounce.send(&self.commands, Command::DoItNow { .. })`.

STORE_ARCHITECTURE.md section 7 puts debounce in the InteractionsStore, and on
the phone that is where the Task/sleep lives. Here it cannot: stores run on the
GPUI thread and rise-engine may never see gpui, so the actor repository — the
only place with a runtime, and the one that already owns the request generation
— is where it goes. Same rule, one layer down.

ENVIRONMENTS
  Resolution order, highest first: RISE_API_URL / RISE_WS_URL in the process
  environment, then config/local.json, then the compiled defaults for RISE_ENV.
  Production ignores the first two — a shipped build that a file on disk can
  repoint at another backend is a credential-theft vector, not a convenience.
  Each environment gets its own data directory and URL scheme, so dev and prod
  never share a database and never steal each other's deep links.

macOS always runs from a bundled .app, never a bare binary: Keychain ACLs,
notifications and now-playing all key off bundle identity.

--------------------------------------------------------------------------------
COMMENTS
--------------------------------------------------------------------------------

The default is NO COMMENT. A comment is a claim that the code could not say this
itself, and nearly always the code could. Two things survive, and nothing else:

  A doc comment on a PUBLIC item of a crate in crates/*.
      Those crates are libraries that other code links against, so their `pub`
      surface is documentation with an actual reader. ONE line. Two or three only
      when the item carries a contract a caller can get wrong: units, ordering,
      what panics, "the row id must be a stable server id". Never longer.

  A single-line // recording a fact that is not in the code.
      A platform quirk, an ordering requirement, a licensing constraint, a
      concurrency / transaction / replay / reconciliation invariant, a gateway
      wire deviation. ONE line. If it needs two, it needs CONTEXT.txt.

Everything else is deleted on sight:

  - every doc comment in app/. `pub` inside a binary is not public API and
    nothing links against it, so there is no reader to document for;
  - doc comments on private, pub(crate) and pub(super) items in crates/;
  - EVERY comment in app/src/modules/*/stores/**. Stores get zero: no file
    headers, no doc comments, no section markers, no inline notes. This is canon
    (../riseonly-ios/STORE_ARCHITECTURE.md section 17), not a preference;
  - multi-paragraph rationale — why this design won, what the alternative was,
    what riseonly-ios does, what PHASES.txt decided, what upstream generates.
    That is what CONTEXT.txt is for, and it is the only place an agent who has
    never seen this repo will actually read it;
  - file-header banners, `// ----` rules, section markers, MARK:, and narration
    of the next five lines;
  - TODO and FIXME. Finish the work, or write the exact entry in
    backend/BACKEND_TODO.txt.

The test, before you type a comment: delete it and read the code. If nothing was
lost it was noise. If what was lost is a DECISION rather than a FACT, it belongs
in that directory's CONTEXT.txt, not above the function.

Comment budget is a review item. A diff that adds prose faster than it adds code
is wrong however well the prose is written.

--------------------------------------------------------------------------------
HOUSE RULES
--------------------------------------------------------------------------------

- gpui is pinned to an exact git rev in the workspace manifest. Never move it to
  a branch, never to crates.io (which is a year stale and predates the
  gpui_platform split). Bumping the rev is scheduled work with a test gate.
- gpui itself is Apache-2.0 and safe to link. The rest of the Zed repo
  (crates/ui, theme, icons, editor, markdown, picker, workspace) is GPL-3.0.
  Read it for reference; never copy it into this product.
- File naming mirrors iOS with one adjustment: directories and file stems become
  snake_case so module paths stay idiomatic (pages/Onboarding/Onboarding.swift
  becomes pages/onboarding/onboarding.rs). Type names are unchanged.
  cargo make parity normalises both sides and measures the result.
- Do not add a dependency without a line in docs/DEPENDENCIES.md explaining why
  it exists and what replaces it if it dies.
