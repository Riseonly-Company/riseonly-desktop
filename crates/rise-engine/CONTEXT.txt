WHAT THIS CRATE OWNS
  rise_wire   typed RPC over one logical socket, correlation by RequestId, and
              the inbound frame classifier.
  rise_store   encrypted SQLite: normalized entities + materialized views for
              realtime sets, resource values for bounded resources.
  rise_sync    generation lifecycle, push reducers batched into one transaction,
              the durable outbox.
  rise_upload  chunked uploads and progress.

  THE WIRE HAS THREE DEVIATIONS FROM THE PROTO. All three are covered by tests
  in rise_wire_frame_decoder.rs and none of them is a bug to fix:
    - `status` is omitted on success by the deployed gateway;
    - the payload is under `data` for some services and `result` for others;
    - `request_id` arrives as a number, a float or a string.

  DTOs are hand-written, never generated by prost. The gateway flattens nested
  proto objects into `data`, so generated structs do not match the wire.

WHAT IT MUST NEVER DO
  Import gpui or an OS crate. Own a socket lifecycle (the host pumps bytes in).
  Contain a feature DTO — those live in each module's engine/.
  Replay a mutation whose idempotency the backend has not confirmed.
